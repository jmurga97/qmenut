# Internationalization

The language panel provides one list: add a language, remove it, or retranslate the
selected branch. Spanish is the default source language. The restaurant's
`default_language_code` is the single source of truth for its default; it is always
available and cannot be removed or translated.

Adding a language makes it available immediately. Missing translations fall back to
the source text. Adding a language or editing the menu never calls the translation
provider. The user explicitly selects **Retraducir contenido** to translate it.

Retranslation requires `languages.write`, an enabled target language and a branch
belonging to the current restaurant. It overwrites names and descriptions of the
branch's non-deleted categories and dishes, variant names, and the names of ingredients
used as extras. Ingredients are shared restaurant entities: translating one also affects
other branches using that same ingredient. Cleared source descriptions clear their old
translations on the next retranslation.

DeepL requests contain at most 50 nonempty texts, use the restaurant's source language,
and preserve description HTML. Output descriptions are sanitized before storage.
Successful batches are saved as they finish; a failure can leave a partial translation.
The public content version is invalidated even after a failure. Retrying re-sends all
texts. `DEEPL_API_KEY` is required; `DEEPL_API_URL` selects the provider endpoint.

Removing a language deletes both its availability and all its translations for the
restaurant in one database batch. Language availability is restaurant-wide; the
retranslation action is scoped to the selected branch.

There is no manual translation editor, hide/activate toggle, coverage dashboard,
automatic-on-add option, pending status, source hash, or translation provenance flag.
Migration `0005_integral_translations.sql` removes the old translation tracking columns;
`0006_simplify_restaurant_languages.sql` removes `is_active` and `is_default` from
`restaurant_languages`. Keep the generated SQL and Drizzle metadata together.

Public UI strings remain bundled in `apps/web/src/lib/i18n/resources`. Menu translations
are database content. Locale codes such as DeepL's `EN-GB` belong in request metadata,
never as prefixes in translated text. Test translation responses must use isolated data;
do not write synthetic provider output into the working local menu database.

Validate the flow with `bun test apps/api/scripts/check-translations.test.ts` and the
Playwright language/content-boundary tests. The isolated Bun check needs a current SQLite
on macOS: set `SQLITE_LIBRARY_PATH` to your SQLite library if the system library cannot
rename tables with qualified CHECK constraints. Its fake provider only writes in memory.
