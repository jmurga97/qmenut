# Internationalization

The language panel adds, edits, completes, retranslates, or removes languages.
The restaurant's
`default_language_code` is the single source of truth for its default; it is always
available and cannot be removed or translated.

Adding a language translates all restaurant branches. A language is published only
when every nonempty source has a nonempty translation matching its current source.
Incomplete languages show a pending count in admin and stay out of the public selector;
requests for them redirect to the default language instead of mixing languages.

Translation writes require `languages.write` and an enabled target language. The editor
validates restaurant/branch ownership and rejects stale source text. It covers category
and dish names/descriptions, variant names, extras, promotions, rewards, and branch
taglines. Shared extras and rewards affect every branch using them. Select a nondefault
content language to edit translations in Languages or the relevant content screen;
the default language continues to edit original content.

Source saves refresh changed machine translations automatically. Manual translations
are preserved and marked for review when their source changes. **Completar traducciones**
retries missing/stale machine translations; **Retraducir contenido** explicitly confirms
overwriting all translations, including manual edits. Cleared source descriptions never
show old translated content. Availability and the admin translation actions are
restaurant-wide; the API also supports an explicitly scoped branch retry.

DeepL requests contain at most 50 nonempty texts within its request-size limit, use the restaurant's source language,
and preserve description HTML. Output descriptions are sanitized before storage.
Successful batches are saved as they finish; a failure can leave a partial translation.
The public content version is invalidated even after a failure, and incomplete results
are never published. Retrying keeps successful current translations. `DEEPL_API_KEY`
is required for automatic translation; manual editing works without it.
`DEEPL_API_URL` selects the provider endpoint. Valencian initially uses DeepL's Catalan
translation and can then be adapted manually.

Removing a language deletes both its availability and all its translations for the
restaurant in one database batch.

Migrations `0007_translation_source_tracking.sql` and `0008_complete_menu_translations.sql`
add source/provenance tracking and the additional translation entities. Deploy migrations
before the API. Existing translations have unknown source provenance: use **Completar
traducciones** or review/save them manually before they become public again. Keep generated
SQL and Drizzle metadata together. No production content is automatically backfilled by
these migrations.

Public UI strings remain bundled in `apps/web/src/lib/i18n/resources`. Menu translations
are database content. Locale codes such as DeepL's `EN-GB` belong in request metadata,
never as prefixes in translated text. Test translation responses must use isolated data;
do not write synthetic provider output into the working local menu database.

Validate the flow with `bun test apps/api/scripts/check-translations.test.ts` and the
Playwright language/content-boundary tests. The isolated Bun check needs a current SQLite
on macOS: set `SQLITE_LIBRARY_PATH` to your SQLite library if the system library cannot
rename tables with qualified CHECK constraints. Its fake provider only writes in memory.
